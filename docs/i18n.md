# Formula internationalization (i18n)

Status: **not wired up.** The engine ships the data; the pipeline is hardcoded to
English. This doc records what works, what breaks, and the exact touch points to
enable it.

## The two representations

A formula has a locale-independent canonical form (what `.xlsx` stores) and a
locale-dependent display form (what a user sees/types). Display language is a
**viewer property**, not a document property — the same file shows `SUM` to an
English user and `SUMME` to a German user, and the argument separator follows the
viewer's regional decimal separator (`,` → `;`).

| | Example | Audience |
| --- | --- | --- |
| Canonical / stored | `_xlfn.MAXIFS(Data!J:J,Data!D:D,$B$1)` | the `.xlsx` format, the engine |
| Display (en) | `MAXIFS(Data!J:J, Data!D:D, $B$1)` | English viewer |
| Display (de) | `MAXIFS(Data!J:J; Data!D:D; $B$1)` | German viewer (`;` separator) |

## What the engine already supports

ironcalc ships `en`, `en-GB`, `de`, `es`, `fr`, `it` (`get_supported_locales()`),
each with a language (function-name table) and a locale (separators/number
symbols). Verified both directions:

- EN → DE display: `SUM(A1:A10)+IF(B1>0,1,2)` → `SUMME(A1:A10)+WENN(B1>0;1;2)`
- DE → canonical: `SUMME(A1:A10)+WENN(B1>0;1;2)` → `SUM(A1:A10)+IF(B1>0,1,2)`

via `Parser::new(locale, language)` + `to_localized_string` / `to_excel_string`.

## What actually happens today (all English)

Driving a German formula through the real API silently corrupts it:

```
set_formula("=SUMME(A1:A3)")  ->  stored "summe(A1:A3)"  ->  recalc #NAME?
set_formula("=SUM(A1:A3)")    ->  stored "SUM(A1:A3)"    ->  ok
```

`SUMME` is unknown to the English parser, so canonicalization emits a mangled
invalid function and the engine resolves `#NAME?`. Excel would reject it too.

## The three hardcoded-English touch points

| Stage | File | Current | German-correct |
| --- | --- | --- | --- |
| Display (read) | `xlcore-export/src/sheet.rs` `strip_formula_decorations` | strips `_xlfn.`/`_xlws.`/`_xlpm.` only; never translates | parse + `to_localized_string(locale, language)` for the formula bar |
| Canonicalize (write) | `xlcore-api/src/dependencies.rs` `formula_parser` / `canonicalize_with_parser` | `new_parser_english` + `to_excel_string` | `Parser::new(locale, language)` so localized input parses → English-canonical OOXML |
| Recalc | `xlcore-bridge` → `xlcore-engine` `WorkbookEngine` | `get_default_language()` = `en` | set viewer locale/language |

## Plan when we enable it

Thread an optional `language`/`locale` parameter from the frontend through the
write setters (`setFormula`, `setRangeFormulas`, `setDefinedName`) and the
formula-bar display:

- Write paths swap `new_parser_english` for `Parser::new(locale, language)`; storage
  stays English-canonical (`to_excel_string` is locale-independent), so files remain
  portable across viewer languages.
- Display side replaces the cheap `strip_formula_decorations` with parse +
  `to_localized_string` parameterized by the viewer's locale. This is the one place
  that trades the ~free string strip for the ~µs-per-formula parse — acceptable
  because the formula bar localizes one cell at a time (lazy, O(1) per selection),
  not the whole sheet eagerly.

Canonical storage is the invariant: read strips/localizes for display, write parses
the viewer's language back to English-canonical. The save path needs nothing — it
writes whatever canonical text is already in the doc.
